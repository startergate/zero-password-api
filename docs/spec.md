# zero-password-api 기획

이 문서는 zero-password-api 에 대해 확정한 내용을 정리한 것이다.
**[계획]** 표시는 하기로 정했지만 아직 구현하지 않은 항목이다.
**[제안]** 표시는 아직 정하지 않은 후보안이다. 하기로 정하면 이 문서를 고친 뒤 구현한다.

---

## 1. 개요

### 1.0 0Password 와 이 저장소

- 0Password 는 비밀번호를 저장하지 않고 사이트별 비밀번호 **규칙**만 모아, 크롬 익스텐션이 로그인 화면에서 보여주는 서비스다. 1.0 은 크롬 웹스토어 출시가 기준이다.
- 세 저장소가 한 방향으로 이어진다: 규칙 데이터 zero-password-db → 이 API → 익스텐션 zero-password-chrome.
- db 는 두 배포판이 있다. 이 저장소는 데이터가 들어 있는 full 버전(npm `zero-password`)을 설치하고, 익스텐션은 데이터 없이 이 API 를 부르는 lite 버전(`zero-password/lite`)을 쓴다.
- 규칙 스키마와 매칭 규칙은 db 저장소가, 화면 표시는 chrome 저장소가 정한다. 이 저장소는 그대로 전달만 한다.

### 1.1 역할

- 익스텐션(zero-password lite)이 부르는 규칙 조회 API 를 서빙한다.
- 크롬 웹스토어 출시에 필요한 짧은 소개 랜딩과 개인정보처리방침 페이지를 서빙한다.
- 하나의 Next.js 앱으로 Vercel 에서 `https://0password.startergate.dev` 로 서비스한다.

### 1.2 하지 않는 것 (1.0)

- 웹 규칙 검색 페이지
- CORS 허용 (웹 페이지에서 직접 호출)
- 규칙 등록·수정 API. 규칙은 db 저장소의 이슈 폼과 PR 로만 추가한다.
- 로그인, 사용자 데이터 저장, 통계 수집

### 1.3 받는 데이터

- 요청 경로의 호스트 이름 하나뿐이다. 비밀번호, 입력 내용, 전체 URL 은 오지 않는다.

## 2. 조회 API

### 2.1 요청

- `GET /api/{domain}`
- `{domain}` 은 익스텐션이 보낸 현재 탭의 호스트 이름이다.
- **[계획]** `GET`, `HEAD` 만 받고 나머지 메서드는 `405`.

### 2.2 응답

- `200 { domain, rule }`
  - `domain`: 실제로 매칭된 DB 항목. 요청과 다를 수 있다 (예: `login.coupang.com` 요청 → `www.coupang.com`).
  - `rule`: `$ref` 를 풀어 낸 규칙 객체 (형태는 db 저장소 spec).
- `404 { error: "not_found" }`: 규칙이 없다.
- 이 형식은 lite 와의 계약이다.

### 2.3 하위 호환

- 응답은 하위 호환을 항상 지킨다. 이미 배포된 익스텐션이 새 응답을 받아도 그대로 동작해야 한다.
- 바꿀 때는 **선택 필드를 추가하는 것만** 한다. 기존 필드를 지우거나, 이름·타입·의미를 바꾸지 않는다.
- 읽는 쪽(lite, 익스텐션)은 모르는 필드를 무시한다.
- `rule` 은 db 의 규칙 객체를 그대로 전달한다. db 가 규칙에 새 선택 필드를 추가해도 이 저장소는 고칠 것이 없다.
- 상태 코드의 의미도 유지한다. lite 는 `404` 만 "규칙 없음"으로 보고, 그 밖의 실패 코드는 오류로 처리한다. 그래서 규칙 없음과 잘못된 입력은 계속 `404` 로 답한다.
- 호환이 깨지는 변경이 필요하지 않도록 만들기 때문에 `/api/v2` 같은 버전 경로는 두지 않는다.

### 2.4 도메인 매칭

- db 의 `findRule` 에 맡긴다 (정확히 일치 → `www.` → 상위 도메인 순). API 는 매칭 로직을 따로 갖지 않는다.

### 2.5 입력 검증

- **[계획]** 소문자로 바꾼 뒤 호스트 이름 형식(영문·숫자·`-`·`.`, 253자 이하)이 아니면 바로 거절한다. 거절 응답은 지금처럼 `404 { error: "not_found" }` 로 둔다 (lite 계약을 바꾸지 않음).

### 2.6 캐시

- **[계획]** 규칙은 하루 한 번만 바뀌고, Vercel 은 새 배포마다 CDN 캐시를 새로 시작하므로 재배포 즉시 반영된다.

| 응답 | Cache-Control |
| --- | --- |
| 200 | `public, max-age=3600, s-maxage=86400` |
| 404 | `public, max-age=600, s-maxage=3600` |

- 익스텐션 쪽 보관 기간은 lite 캐시가 따로 정한다. `max-age` 는 브라우저 HTTP 캐시에만 해당한다.

### 2.7 CORS

- CORS 헤더는 보내지 않는다. 익스텐션은 `host_permissions` 로 호출한다.

### 2.8 위치

- 지금 API 는 Pages Router(`pages/api/[domain].ts`), 화면은 App Router(`app/`)에 있다.
- **[계획]** API 를 `app/api/[domain]/route.ts` 로 옮겨 App Router 로 통일한다. 주소와 응답은 그대로이고 `next.config.ts` 의 `outputFileTracingIncludes` 키만 새 경로에 맞춘다.

## 3. 페이지

### 3.0 언어

- **[계획]** 페이지는 언어별 경로 `/{lang}/...` 로 나눈다. 지원 언어는 `ko`, `en`.
- **[계획]** 언어가 없는 주소(`/`, `/privacy`)는 브라우저 설정(`Accept-Language`)을 보고 `/ko/...` 또는 `/en/...` 로 리다이렉트한다. 지원하지 않는 언어는 `en` 으로 보낸다.
- API(`/api/...`)는 언어와 상관없다.

### 3.1 소개 랜딩 (`/{lang}`)

- **[계획]** create-next-app 기본 화면을 교체한다.
- 내용: 한 줄 소개, 로그인 화면에서 규칙을 보여 주는 예시 그림 1장, 크롬 웹스토어 설치 버튼, 규칙 제보 링크(db 저장소 이슈 폼), 개인정보처리방침 링크.
- 웹스토어 주소가 생기기 전에는 설치 버튼을 "준비 중"으로 둔다.
- **[계획]** README 도 프로젝트 설명으로 교체한다.

### 3.2 개인정보처리방침 (`/{lang}/privacy`)

- **[계획]** 방문 사이트 도메인을 API 로 보내는 것은 웹스토어 정책상 web browsing activity 처리라서 방침 페이지가 필요하다.
- 담을 내용:
  - 보내는 것: 로그인 화면을 찾았거나 팝업을 열었을 때 그 탭의 호스트 이름. 규칙 조회에만 쓴다.
  - 보내지 않는 것: 비밀번호, 입력 내용, 전체 URL·경로·쿼리, 쿠키, 계정 정보.
  - 서버 저장: 따로 저장하지 않는다. 호스팅(Vercel) 접근 로그에 요청 경로가 남을 수 있고 보관 기간은 Vercel 정책을 따른다.
  - 익스텐션 안: 받아 온 규칙만 `chrome.storage.local` 에 캐시한다.
  - 제3자 제공·판매 없음, 문의처.
- **[계획]** 언어별로 페이지를 나눠 `/{lang}/privacy` 로 둔다: `/ko/privacy`, `/en/privacy` (웹스토어 심사 대비 영어 포함).

## 4. 데이터

- npm 패키지 `zero-password` 의 full 버전을 의존성으로 설치해 패키지 안의 `databases/` 를 읽는다.
- `databases/` 는 요청 시점에 경로를 만들어 읽기 때문에 Next 파일 추적이 못 찾는다. `next.config.ts` 의 `outputFileTracingIncludes` 로 API 번들에 포함한다.
- 버전은 `bun.lock` 으로 고정된다. 새 규칙은 패키지 버전이 올라가고 lock 이 갱신돼야 API 에 반영된다.

## 5. 배포

### 5.1 지금

- `main` 머지 → Vercel 자동 배포.
- 규칙 갱신은 수동: db npm 배포 → 이 저장소에서 의존성 갱신 → `main` 머지.

### 5.2 하루 한 번 자동 재배포

- **[계획]** 지난 배포 뒤 바뀐 규칙이 있을 때만 하루 한 번 npm 배포와 API 재배포가 자동으로 돈다 (전체 기획 확정).
- **[계획]** 흐름:
  1. db 저장소 Actions 가 매일 돌아, 바뀐 규칙이 있으면 패치 버전을 올려 npm 에 배포한다 (db 저장소 참고).
  2. 배포가 끝나면 이 저장소에 `repository_dispatch` 를 보낸다.
  3. 이 저장소 Actions 가 `main` 에서 브랜치를 따서 `bun update zero-password` 로 `bun.lock` 을 갱신하고, `main` 으로 PR 을 연다.
  4. 빌드 검사가 통과하면 PR 이 자동 머지된다. 실패하면 머지되지 않고 PR 이 남는다.
  5. `main` 머지로 Vercel 이 다시 배포한다.
- Vercel Deploy Hook 만 부르는 방식은 `bun.lock` 이 이전 버전을 고정하고 있어 새 규칙이 들어오지 않으므로 쓰지 않는다.
- **[계획]** 자동 갱신은 `develop` 에 반영하지 않는다 (머지 커밋이 너무 잦아짐). 대신 `main` 대상 PR 에서 `bun.lock` 의 `zero-password` 버전이 `main` 보다 낮으면 실패하는 Actions 검사를 두고, 브랜치 보호의 필수 검사로 건다. 이 검사가 실패하면 `main` 의 `bun.lock` 을 `develop` 에 맞춘 뒤 다시 머지한다.
